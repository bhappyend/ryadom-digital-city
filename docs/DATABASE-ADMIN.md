## Accounts repository (API04.1)

`new AccountsRepository(poolOrPoolClient)` composes inside exported `withTransaction(pool, async client => ...)` without nested BEGIN. Source types in packages/db/src/accounts.ts are authoritative. CreateUser/UserInput: email, passwordPhc, displayName, termsVersion, privacyVersion; optional session creates account/roles/consents/session atomically. bootstrapSuperAdmin adds emailVerifiedAt and requires context+operator reason; advisory singleton, no default account, password or MFA bypass. Explicit API CLI verifies bootstrap authorization before calling.

- findUserByEmail(email): private snake_case user row|null; getAuthUser(id): row+account DTO+mfa credential+unconsumed recoveryCodes{id,digest}; getAccount(id): validated Account.
- createSession(SessionInput): userId/tokenDigest/csrfDigest/assurance/idleExpiresAt/absoluteExpiresAt/optional stepUpUntil. findSession(digest): live status/security-version/expiry checked row, plus sessionId/userId/csrfDigest/stepUpUntil/account aliases; timestamps are pg Dates. revokeSession(actorUserId,sessionId) is scoped before mutation, foreign id NOT_FOUND.
- createChallenge(ChallengeInput): nullable userId for preauth, kind, tokenDigest/csrfDigest/expiresAt/optional encryptedSecret. findChallenge/attemptChallenge/consumeChallenge operate on digest. `attemptChallenge` must execute outside the later failed verification transaction so attempts commit. At most five attempts, consumption single winner. Caller verifies code/CSRF/time and binds the correct challenge kind/user.
- getMfa, setMfa(userId,EncryptedEnvelope,step,recoveryDigests[10]), consumeTotp(userId,step), consumeRecovery(userId,digest). TOTP monotonic step and recovery single consume are conditional atomic UPDATEs; combine with challenge consume/session issue in one transaction. Recovery hashing/verification, TOTP cryptography, AAD and key storage are API responsibilities.
- setRoles(userId,roles,expectedVersion,context): requires live super-admin, prohibits self grant, revokes sessions and increments security version with audit. SQL triggers protect last active super-admin from role removal/status suspension. Status changes also prohibit ordinary Admin suspending Admin/Super Admin.

## Admin repository (API04.1)

`new AdminRepository(pool,{encrypt?,decrypt?})`. Phone list DTO only visibility/hasValue; no encrypted envelope is returned to browser.

`execute(operationId,{params?,query?,body?},{actorId,requestId})` parses current accounts registry schemas and rechecks live account permissions. Returns data, not transport envelope. API remains responsible for session/cookies/MFA/step-up/Origin/CSRF/distributed rate limits and response validation. Unknown/unimplemented capability throws INVALID_STATE, never successful empty write. Public actorId may be null only for public operations.

New manual records have stable manual-UUID slug, draft inactive until explicit publish, registered source/license/attribution required. patchvale-admin source registration is an operator provenance namespace, not independent rights verification. Any place_field_overrides causes ImportRepository.upsertPlace to throw explicit editorial ownership review error before changing source/counters/place. ## Manual monthly settlement

Administrative lookup: execute `listAdminListings` with query page1..100/limit1..50, optional literal business-name q2..200, ownerId/placeId UUID, placement status; `getAdminListing` with listingId. Both use current registry listing:quote live permission (Admin/SuperAdmin/BusinessManager), while API enforces mandatory admin MFA. Reads use a repeatable-read readonly transaction so page totals, items and embedded current references share a consistent snapshot. Stable order createdAt DESC/id DESC; empty page preserves total. Literal LIKE escapes %, underscore and backslash, all SQL values parameterized.

Lookup projects current offer amount/month/RUB/terms/date, actually accepted current agreement, authoritative ownerId/displayName and this listing's actual receipt-linked funded summary. Owner resolves current agreement owner first, otherwise CRM account_id matching applicant; CRM-reference links never establish owner/funding. Missing owner/offer/agreement/funded entitlement are null, never invented. Funded summary requires published+verified listing and begun funded period. No phone, ciphertext, password or applicant email in DTO. Unknown detail returns NOT_FOUND. No new tables, grants, dependencies or migrations.

Immutable offer→separately recorded real external agreement→actual receipt ledger. `quoteListing` emits quoteId and null agreementId until actual recordFounderAgreement. Agreement binds owner/offer/customer acceptance/reference/channel/timezone/original monthly anchor; receivedAt cannot precede acceptance or be future. Record/confirm idempotency uses UUID+payload SHA256; exact replay returns current projection of the same durable mutation, changed payload CONFLICT. Listing row lock, unique receipt/key/period start, explicit overlap query, original anchor calendar-month arithmetic including Jan31→Feb28→Mar31. Latest offer only; requote needs fresh agreement. No automatic charge or contact-click activation.

Payment changes pending-payment→pending-review, never publishes or verifies ownership. Subscription projection is pending until funded AND published AND verified; real owner summary null absent these gates, otherwise receipt/agreement-linked actual period (earliest active end, else latest past). Expiry is evaluated on every read; no invented grace. A future funded period does not grant current entitlement. Quote amount is positive operator input; no global default monthly price is seeded.

## Privacy and limits

Media upload tickets expire after exactly five minutes (300000ms) from server transaction creation. Both ticket lookup and completion require expires_at strictly greater than the database clock; equality/expiry is denied. Expired completion does not set ready state, metadata or append media.ready audit. Ticket creation audit remains as evidence of the original request.

owner_phone_reveals stores immutable owner/actor/reason/requestId/auditFK/time, no phone or ciphertext. Authorization record commits before decrypt callback; storage failure rolls back audit and returns no phone. Each reveal is a separate audited read; no client idempotency key exists. Reason must not repeat the phone or unnecessary personal details. Proposed retention30days is provisional pending operator/legal policy; no automatic destructive retention job is enabled. Audit append-only preserves investigation evidence; an explicit privileged maintenance procedure is needed for approved erasure/retention. Keys stay outside DB/runtime browser. Test crypto is a reversible synthetic fixture only and is never production encryption.

Not implemented by this DB slice: account deletion/purge/export jobs, favorites, organization proposals/branch changes, subscription cancellation/refunds, generalized SQL/FS console, automatic importer override reconciliation. API must explicitly expose unavailable for unsupported operations. DB backup/restore with new private tables, encryption key recovery, load/p95 and retention operations remain production gates.

## Ownership activation continuation

`AdminRepository.execute` now delegates the existing six claim/listing-decision operations to the internal `OwnershipRepository`. Input parsing and live permissions remain at the common repository boundary, while session assurance, Origin/CSRF, fresh MFA and distributed limits remain API responsibilities. Approval returns the shared ListingWithSubscription projection, not a placeholder receipt. Applying for a listing snapshots an existing pending/verified claim under the same per-place advisory lock as claim decisions.

Additive `004_ownership_claims.sql` creates owner_claims, immutable ownership_claim_decisions and listing_review_decisions with audit references, one verified claim per place, and bounded evidence/notes. No fixture or automatic owner creation. All claim/membership/branch/listing updates and audit records commit together. Verification serializes competing place claims; CAS rejects repeat/stale decisions. Claim withdrawal is applicant-scoped. Verification and publication lock the applicant status row, and reject inactive applicants. Staff self review is forbidden. Verified business membership never modifies emailVerified, MFA credentials or auth roles. Publication requires current actual agreement, matching current-period receipt, verified live membership and licensed published catalog data. Revocation demotes affected published applications and clears applicable membership without deleting original catalog/source data.
